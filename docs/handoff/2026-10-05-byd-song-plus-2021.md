## 4. 仪表歌词（原有实现与本轮优化）

- **功能**：在比亚迪仪表的音乐卡片里显示 CarPlay 当前歌曲（"歌名 — 歌手"）以及播放/暂停。音乐 App 打开"车载/蓝牙歌词"后，歌名字段里放的是当前歌词，所以仪表显示的就是歌词。
- **来源**：参考 DiPlay 上游 [PR #101](https://github.com/shihabal3amri/DiPlay/pull/101)、[PR #215](https://github.com/shihabal3amri/DiPlay/pull/215)。本分支的提交是 `069b588`（新增）和 `1023bb5`（移除"仅在换歌时显示"开关）。
- **设置**：设置 → 车辆 → 比亚迪分组 →"仪表显示歌曲/歌词"，默认关闭。需要先授权车机网络 ADB。
- **代码**：`shared/.../hud/BydClusterSong.kt`、`ClusterSongWriterSession.kt`、`ClusterWriterProtocol.kt`、`BydVehicleDataTool.kt`（使用 `clustersongwatch`；一次性 `clustersong` 诊断模式已于 2026-10-06 删除，见第 14 节）。
- **实车结果（2026-10-05）**：
  - 写入成功，日志里每次都是 `Cluster song: clustersong source=0 state=0 text=0`，返回码 0 表示成功；
  - 仪表能显示，但**有约 1–2 秒延迟**，歌词变化快时会滞后；
  - 延迟原因：每次更新都会新起一个 `app_process` 进程。
- **"仅在换歌时显示"已移除**：开着歌词时，歌名每句都在变，程序无法区分"换了一句歌词"和"换了一首歌"，这个开关没有意义。
- **当前状态**：本轮已改为会话内复用常驻进程；本次又增加了 1 秒 mailbox 读失败宽限、恢复日志和会话内最多两次 helper 重启。模拟器单元测试通过，实车需重点确认歌词不会因短暂 ADB/文件读失败消失。

### 9.3 退出与恢复

- 菜单退出先关闭 CarPlay 会话连接及服务监听，再等待网络、媒体和辅助资源清理，最后结束 Activity 和应用进程。
- 蓝牙恢复等待主线程操作，检查优先级读回及重连结果；失败保留恢复记录供下次重试。单项失败不阻止其他清理。
- P2P 移除等待回调并确认组不存在；启动过程中退出也会清理。清理失败会记录失败，不再一律报告成功。
- 关键日志：`shutdown reason=settings exit application`、`exit cleanup wireless=... bluetoothRestored=... wifiSearchResumed=...`、`shutdown complete`。

### 9.4 常驻歌词写入

- CarPlay 会话激活且仪表歌词已开启时只启动一个 `app_process`。复用 SDK 实例和当前固件信号 ID，停止逐条歌词启动 JVM。
- 使用 `getExternalFilesDir("cluster")` 下的会话文件；启动前验证 ADB shell 能读取。没有假定 shell 可以读取应用私有 `/data/data`。
- 原子替换最新状态文件，进程每 100ms 读取；更新只消费最新序号，跳过积压的旧歌词。App 每秒刷新心跳，重复心跳不重复写仪表。
- 正常断开、控制器关闭、菜单退出、关闭选项均写 STOP，尝试将仪表置为停止并清空文本，随后退出并删除会话文件。
- App 异常退出后，心跳失效约 3 秒触发退出。helper 对原子替换造成的短暂 mailbox 读空保留 1 秒宽限，恢复后继续消费最新歌词；独立 watchdog 对短暂读空不提前清卡，持续失联、STOP 或 SDK 写入卡死时仍按约 1 秒宽限清卡并终止进程。ADB 流异常时会在当前 CarPlay 会话内最多重启两次 helper，实际 SDK 完全阻塞时清卡仍属于尽力操作。
- 旧会话迟到的回调不能停止新会话。旧进程退出未确认时阻止新进程启动；进程全局文件锁再防止并存。ADB 异常后的兜底仅对匹配 helper 类、模式及会话 token 的 PID 发信号。
- 日志带 token、PID、`seq`、`ageMs`、`skipped`、SDK 返回码及 `processGone`；不记录歌词正文。

## 10. 通话降风量（2026-10-05，基于已推送的 b53d7f1）

- 本节新增改动尚未提交、未推送。
- 用户确认增加“CarPlay 通话时降低空调风量”独立设置，默认关闭。开启后，CarPlay 的 `phoneCall` 状态进入 active 时启动独立 helper；通话状态结束、CarPlay 会话结束、控制器关闭、应用退出或关闭设置时删除请求文件并释放。手动测试仍保留作诊断，不改变自动联动开关，与仪表歌词独立。
- 固件证据：原车 HiCar 调用 `AudioManager.setCallState(1, 2)`，结束用 `(1, 0)`。`IAudioService` 将状态转给 `DenoiseFocusControl`，再发送 MCU 通话状态；固件有 `wind_decrease_for_bt` 设置。CarPlay 当前只记录 `phoneCall` 状态，日志显示 HFP 已断开、`audioMode=0`，缺少这条通知链路。
- 对原车 `framework-dex` 的检查确认：`AudioManager` 包装方法会吞掉 `RemoteException`。helper 直接通过 `IAudioService` 反射复现 HiCar 的完整进入顺序 `setCallState(1,2)` → `setMuteState(1,true)` → `setMode(MODE_IN_CALL)`；通话状态和音频模式带本 helper 的 Binder token。释放按 `setMuteState(1,false)` → `setCallState(1,0)` → `setMode(MODE_NORMAL)`，仅回滚尝试过的步骤，中间步骤失败也继续回滚。不会直接设置风量档位。
- 测试入口位于设置 → 车辆 → 比亚迪。空闲时手动启动，发送完整通话序列并保持 10 秒，之后发送释放状态；运行中可以点击停止。自动联动使用同一 helper 协议，但请求文件保持到 CarPlay 通话结束，另有 30 分钟安全上限。关闭设置、会话断开、控制器关闭、应用退出会取消；Activity 销毁和手动停止按钮只取消手动测试，不影响后台 CarPlay 自动通话。保留现有日志保留及导出逻辑。
- 手动测试启动前拒绝正在进行的 CarPlay 通话。手动和自动模式均拒绝非普通系统音频模式、原车蓝牙电话、HiCar 电话、紧急呼叫及仍连接的 HFP；实际请求前再次检查。普通电话和微信的 `phoneCall` 状态都会触发自动序列，Siri 状态不作为电话。冲突时记录 blocked，不强抢原车状态。
- App 使用应用外部目录下的会话请求文件取消 helper；自动模式每秒刷新文件租约，以单调时钟衡量文件连续 5 秒未变化，避免校时影响超时；单进程测试锁防止重叠。进入序列和释放互斥，watchdog 先标记取消再等待进入结束，不会释放后又执行剩余静音/模式请求。helper 带独立 watchdog（手动最长 15 秒、自动最长 30 分钟，触发后约 1 秒强制退出）。通话状态和模式有 Binder 归属，但 BT 静音为共享状态，不能声称强杀时全部状态都自动恢复；Binder 卡死及原车并发仍须实车验证。
- 成功提示只表示系统服务接受了释放调用，不声称风量已改变。真实降风量及恢复需要观察车机；车机原有“通话降低风量”开关须开启。

## 13. 通话降风量改用公开空调接口（2026-10-06）

### 13.1 依据

- 用户提供的 `byd_updatefull/bydauto-openapi.jar` 只是编译用的接口存根；固件 framework 中有同名真实实现，已反汇编对照。
- `BYDAutoAcDevice` 的设备类型为 1000。`setAcWindLevel(source, level)` 写入 `AC_WIND_LEVEL_SET` 和 `AC_CTRL_SOURCE_SET`，固件接受 0–7 档。可读取 `getAcStartState`、`getAcControlMode`（0 自动/1 手动）、`getAcWindLevel`。
- `BYDAutoSettingDevice.getACBTWind/setACBTWind` 只读写原车“通话降低风量”开关，不能触发降风量。
- 权限分两层：
  - Java 层只有 `getInstance()` 检查 `BYDAUTO_*_COMMON`，shell 没有这个权限，改用构造函数即可绕开。
  - 原生 `libbydautoservice.so` 的 `BYDAutoService::checkSetPermission` 对调用方 UID ≤ 9999 直接放行，与设备类型无关；应用 UID 还需要逐项的 `*_SET` 权限，应用拿不到。
- 第 12 节 shell 写 MCU 失败的报错 `Neither user 2000 … BYDAUTO_SETTING_COMMON` 来自 Java 层 `getInstance`，不是原生层拒绝。
- `libbydauto.so` 的 set 会同步等待车辆回执（`waitResponse`、`finishCommand: return timeout`），可能耗时。

### 13.2 实现

- 设置 → 车辆 → 比亚迪：保留“CarPlay 通话时降低空调风量”开关（默认关）。新增“通话时风量档位”，可选 1–3 档，默认 2 档，下一通电话起生效。
- 触发与生命周期沿用原来的 helper、请求文件租约、watchdog 和手动 10 秒测试。helper 改为 `AcWindReduction`，通过 `BydVehicleDataTool.sdkDevice` 获取设备，`getInstance` 失败时回退到构造函数。
- 进入通话时读取空调开关、控制模式和档位，以下情况记为 `blocked:` 不动风量：
  - 空调未开；
  - 档位未知（如 65535）；
  - 当前档位已不高于目标档；
  - 原车蓝牙电话、HiCar 或紧急呼叫正在进行（交给原车处理）。
- 否则调用 `setAcWindLevel(触屏来源 0, 目标档)`，返回 0 才算成功，并在 1.5 秒内读回确认。
- 结束时：
  - 空调仍开且档位仍是目标档，才恢复：原为自动模式则调 `setAcControlMode(0, 自动)`，原为手动模式则恢复原档位；
  - 否则保留驾驶员或车辆在通话中的改动。
  - 下发失败但车辆实际已执行（读回是目标档）时，也会恢复。
- 因为 set 要等车辆回执：helper 释放宽限从 1 秒改为 5 秒（`RELEASE_GRACE_MS`）；应用侧停止时等待 6 秒后才强制结束 helper；`cancel` 每项等待从 6 秒改为 8 秒。
- 已删除 `IAudioService` 的 `setCallState`、静音和 `setMode` 整套调用，以及 HFP、音频模式冲突检查，因此不再有“媒体声音变小”的副作用。
- 原车开关的值只写入日志（`stockCallWind=`），功能不依赖它。
- 日志不改变清理和导出机制，关键行：
  - `ac power=… mode=auto|manual level=… target=… stockCallWind=…`
  - `ac fan set level=… result=… success=…`、`ac fan readback level=…`
  - `ac restore mode=auto|level=… result=…`、`ac restore readback …`
  - `ac restore skipped: …`、`blocked: …`
